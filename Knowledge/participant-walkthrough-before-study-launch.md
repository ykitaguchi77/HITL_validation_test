# 被験者実験の実施前に「被験者になりきったウォークスルー」で手順書・運用・計測方針の穴を洗い出す

- type: technique
- created: 2026-09-15
- tags: [experimental-design, HITL, user-study, protocol, annotator-guide, measurement]

## 要点
実装・設計レビューを何度重ねても、**手順書と実 UI の乖離・被験者が迷う場面・計測の意味を変える未規定の行動方針**は
開発者視点では見落とされる。データ収集を始める前に、配布資料だけを頼りに**初回ログインから最終セッションまでを
被験者の一人称で追体験(ナラティブ・ウォークスルー)**し、「引っかかった点」を列挙して潰す。

## 適用場面 / 状況
- 少人数(数名)のアノテータ/被験者に、ブラウザ webapp 等で長時間(数時間)のタスクを課す実験の直前。
- 設計変更(アノテータ名の実名化・セッション構成変更など)を繰り返した後で、配布資料が追随しているか不安なとき。
- 本プロジェクト: 練習2 + Scratch + Session 1〜9 = 12セッション・106枚・2〜3時間の HITL アノテーション実験。

## 内容
1. **入力は配布資料のみ**にする(手順書・URL・パスワード)。コードや設計書は見ない。
2. ログイン → 練習 → 本番 → 中断/再開 → 最終セッションまで、**各ステップで「何が見え、何を押し、何に迷うか」**を書く。
   時間感覚(1枚何分・何枚目で疲れるか)と主観負荷も想像で入れる。
3. 出てきた「引っかかり」を次の3種に分類して対処する:
   - **手順書 ⇔ UI の乖離**(例: 「アノテータ番号 1/2/3」と書いてあるが画面は実名) → 手順書を即修正。
   - **被験者が迷う操作**(例: 楕円回転は練習3枚中1枚しか経験できない) → 練習の再実施を案内・練習画像を追加。
   - **計測の意味を変える未規定の行動方針**(例: 予測が悪いとき「削除→描き直し」を許すか、必ず修正するか) →
     **指示文で明示し、解析方針(その行動をどう集計するか)も事前に決めて文書化**する。これは事前解析計画の一部。
4. 運用面(休憩・分割実施の目安・同じ PC/ブラウザの使用)も手順書に書く。被験者が自分で計画できる。

## 注意点・落とし穴
- 「精度の基準」(何 px まで合わせるか)を伝えるか否かは結果に効く判断。伝えれば均質化するが「ふだん通り」から離れる。
  どちらにするか決めて手順書に反映し、論文の Methods にも書く。
- ウォークスルーは想像なので、実施後に**本物の被験者1名の初回セッションを観察**して答え合わせをするのが望ましい。
- 手順書の修正は割付やコードに影響しないので気軽に行えるが、**修正後の版を全員に配り直す**こと(版の混在はプロトコル逸脱)。

## 追記 (2026-09-15)
- 出典: Experimental_record/20260915.md(追記4)
- ウォークスルーで抽出した「手順書 ⇔ UI の乖離」と「未規定の行動方針」の2点を同日中に手順書へ反映した
  (アノテータ選択の実名化・「予測の直し方は自由(修正でも削除→描き直しでも可)」の明記)。
- **未規定の行動方針を「自由」と決めるときは、その行動がログのどの列に現れるかを同時に確認する**こと。
  本件では `shapes_deleted > 0` が「予測を捨てて描き直した」の識別子になり、**描き直し率 vs モデル成熟度**を
  副次指標として追加できる。逆に描き直し画像では `vertices_edited`/`correction_dice` の意味が変わるので、
  事前解析計画に「描き直し画像の扱い」を書いておく。
- 手順書修正は `str.replace` + `assert old in s` で対象文を厳密一致させ、`git diff --stat` で意図した行だけが
  変わったことを確認すると安全(長い日本語 Markdown の部分編集は誤マッチしやすい)。

## 追記 (2026-09-19) — 想像のウォークスルーが拾えない穴 = 「発見性」
- 出典: Experimental_record/20260919.md
- 設計置換後に**実ユーザー(研究者本人)が実機を触った**ところ、想像のウォークスルーでは出なかった要望が出た:
  「ドラッグで点をまとめて選択して動かしたり消したりしたい」。実際は Ctrl+ドラッグでの複数選択+移動が 2 か月前に実装済みで、
  **機能はあるのに発見されていなかった**(修飾キーが要る操作はヒント文 1 行では伝わらない)。一括削除だけが本当に未実装だった。
- 含意: 開発者視点のウォークスルーは「知っている操作」を前提に進むため、**発見性の穴(存在するが見つからない機能)は構造的に拾えない**。
  被験者実験では発見の有無が被験者間で労力指標(頂点編集数・時間)のばらつきになるので、計測の妥当性の問題でもある。
- 対策の型: ①状態に応じて「今できる操作」を常時表示するパネル、②初回セッションで自動表示される図つきチュートリアル(`?` で再表示、
  閲覧中は計時停止)、③手順書の操作表にも同じ内容を載せる。実ユーザー 1 名の試用は注意点に書いた「答え合わせ」そのもので、
  データ収集前に必ず 1 回入れる。

## 追記 (2026-09-19) — 疲労閾値とキー操作の「期待」も実試用でしか出ない
- 出典: Experimental_record/20260919.md(フィードバック②)
- 同じ試用の 2 巡目で「12 枚/セッションはしんどい → 10 枚に」「矢印キーはポリゴン全体でなく選択中の 1 点を動かしてほしい」が出た。
  どちらも設計者は「所要時間 1.5〜2 h なら妥当」「矢印 = 選択対象を動かす」と考えていて、想像のウォークスルーでは検出できない種類の穴
  (身体的負荷の閾値、操作の意味の期待)。
- 含意: **セッション枚数・操作の意味は「変えられる前提」で作っておく**。割付生成はセッション枚数をスロット数から独立したパラメータにし
  (→ Knowledge/session-size-decoupled-from-slot-count-balanced-omission.md)、キー操作は選択単位の優先順で決める
  (→ Knowledge/hitl-annotation-webapp-konva.md)。実試用の指摘を当日中に反映し、再生成 → 検証 → 文書のハッシュ・文言更新までを 1 セットにする。

## 追記 (2026-09-20) — 被験者向け表記は「模範解答」に統一し、研究者語「正解(GT)」は UI から外す
- 出典: Experimental_record/20260920.md(練習 1 の教示文言の書き換え)
- 実試用の 2 巡目で研究者本人から「練習の最初の文言を『練習のみ、完成後に模範解答が出ます。微妙な部分のニュアンスを確認し、
  本番でも模範解答と同じようなアノテーションができるように練習してください』のニュアンスに」と指示が出た。
  それまでの UI は「正解(GT)が点線で表示 / 正解と同じ精度が目標」と書いていた。
- 含意: 「正解(GT)」は**採点基準としての真値**を連想させ、被験者に「合っているか採点される」印象を与える。「模範解答」は
  **見習うべき手本**の枕で、練習の目的(境界のニュアンスを学び本番で再現する)に合う。被験者が読む文言(開始モーダル・サイドバー・
  提出後の status・チュートリアル・配布ガイド)は前者を避け、研究者向け文書(計画書・OSF・解析コード)だけ GT のままにする。
- 手順: 表記を変えるときは `grep -n "正解" static/js/*.js *.md` で**全出現箇所を列挙してから**一括置換し、残りが 0 か
  研究者向けの文脈だけかを確認する(本件では提出後 status の 1 か所が取り残され、grep で拾って追加修正)。文言だけの変更でも
  `app_version` が変わるようにしておけば(→ Knowledge/stale-frontend-after-server-fix-version-handshake-reload.md)、被験者側の
  ブラウザは次セッション開始時に自動で新文言へ切り替わる。
