# 被験者実験の実施前に「被験者になりきったウォークスルー」で手順書・運用・計測方針の穴を洗い出す

- type: technique
- created: 2026-09-15
- tags: [experimental-design, HITL, user-study, protocol, annotator-guide, measurement]

## 要点
実装・設計レビューを何度重ねても、**手順書と実 UI の乖離・被験者が迷う場面・計測の意味を変える未規定の行動方針**は
開発者視点では見落とされる。データ収集を始める前に、配布資料だけを頼りに**初回ログインから最終セッションまでを
被験者の一人称で追体験(ナラティブ・ウォークスルー)**し、「引っかかった点」を列挙して潰す。

## 適用場面 / 状況
- 少人数(数名)のアノテータ/被験者に、ブラウザ webapp 等で長時間(数時間)のタスクを課す実験の直前。
- 設計変更(アノテータ名の実名化・セッション構成変更など)を繰り返した後で、配布資料が追随しているか不安なとき。
- 本プロジェクト: 練習2 + Scratch + Session 1〜9 = 12セッション・106枚・2〜3時間の HITL アノテーション実験。

## 内容
1. **入力は配布資料のみ**にする(手順書・URL・パスワード)。コードや設計書は見ない。
2. ログイン → 練習 → 本番 → 中断/再開 → 最終セッションまで、**各ステップで「何が見え、何を押し、何に迷うか」**を書く。
   時間感覚(1枚何分・何枚目で疲れるか)と主観負荷も想像で入れる。
3. 出てきた「引っかかり」を次の3種に分類して対処する:
   - **手順書 ⇔ UI の乖離**(例: 「アノテータ番号 1/2/3」と書いてあるが画面は実名) → 手順書を即修正。
   - **被験者が迷う操作**(例: 楕円回転は練習3枚中1枚しか経験できない) → 練習の再実施を案内・練習画像を追加。
   - **計測の意味を変える未規定の行動方針**(例: 予測が悪いとき「削除→描き直し」を許すか、必ず修正するか) →
     **指示文で明示し、解析方針(その行動をどう集計するか)も事前に決めて文書化**する。これは事前解析計画の一部。
4. 運用面(休憩・分割実施の目安・同じ PC/ブラウザの使用)も手順書に書く。被験者が自分で計画できる。

## 注意点・落とし穴
- 「精度の基準」(何 px まで合わせるか)を伝えるか否かは結果に効く判断。伝えれば均質化するが「ふだん通り」から離れる。
  どちらにするか決めて手順書に反映し、論文の Methods にも書く。
- ウォークスルーは想像なので、実施後に**本物の被験者1名の初回セッションを観察**して答え合わせをするのが望ましい。
- 手順書の修正は割付やコードに影響しないので気軽に行えるが、**修正後の版を全員に配り直す**こと(版の混在はプロトコル逸脱)。

## 追記 (2026-09-15)
- 出典: Experimental_record/20260915.md(追記4)
- ウォークスルーで抽出した「手順書 ⇔ UI の乖離」と「未規定の行動方針」の2点を同日中に手順書へ反映した
  (アノテータ選択の実名化・「予測の直し方は自由(修正でも削除→描き直しでも可)」の明記)。
- **未規定の行動方針を「自由」と決めるときは、その行動がログのどの列に現れるかを同時に確認する**こと。
  本件では `shapes_deleted > 0` が「予測を捨てて描き直した」の識別子になり、**描き直し率 vs モデル成熟度**を
  副次指標として追加できる。逆に描き直し画像では `vertices_edited`/`correction_dice` の意味が変わるので、
  事前解析計画に「描き直し画像の扱い」を書いておく。
- 手順書修正は `str.replace` + `assert old in s` で対象文を厳密一致させ、`git diff --stat` で意図した行だけが
  変わったことを確認すると安全(長い日本語 Markdown の部分編集は誤マッチしやすい)。
