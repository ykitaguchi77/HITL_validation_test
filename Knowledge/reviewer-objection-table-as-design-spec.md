# 被験者実験を設計し直すときは「想定される査読の突っ込み → 設計上の対策」表を仕様の中核に置く

- type: pattern
- created: 2026-09-19
- tags: [experimental-design, user-study, HITL, paper-writing, reviewer, planning, dose-response]

## 要点
「論文で突っ込まれそうなところをつぶし、新規知見が役立つデザインにしたい」という方針で実験を設計するときは、
条件・枚数・解析を個別に決める前に、**想定される査読コメントを 1 行 1 件で列挙し、各行に「設計で潰す具体策」を対応させた表**を
書き、その表から条件構造・割付・事前計算物・解析式を導く。未決定の設計項目(学習レシピ・セッション構成など)は、
この表の行を満たす選択肢に絞ると、ユーザーへの確認往復なしに決められることが多い。

## 適用場面 / 状況
- 別プロジェクトの新知見(例: SAM decoder-LoRA の n-shot 学習)で既存の被験者実験を作り直すとき
- ユーザーが個別の設計項目への即答を保留し、代わりに「査読対策」「新規性が活きる」といった**方針**を示したとき
- 本プロジェクト(2026-09-19): SegFormer 8 条件設計を「n-shot 用量反応・ランダム化」へ置換する計画で、
  保留 2 点(LoRA 学習レシピ / 1 人あたり構成)を表から導いた

## 内容
1. 表の左列は「査読者の言い方」で書く(例: 「n の効果は特定の学習画像の当たり外れでは?」「提案が速いのは精度を犠牲にしているだけ」
   「タイミングで条件が分かる」「学習セットと評価画像の患者リーク」「1 epoch/枚は妥当か」「新規性は?」)。
2. 右列は**実装に落ちる粒度**で書く(seed 数と割当比、ゲート閾値の決め方、共変量名、assertion の有無、事前計算する指標名)。
   「Limitations に書く」は対策ではなく、右列に書かない(書くなら別欄で「受容する限界」と明示)。
3. 表が埋まったら、そこから**逆算**して設計仕様を書く:
   - 「当たり外れ」行 → 学習順を複数 seed にし、seed を割付と解析に組み込む
   - 「speed–accuracy」行 → 主要評価を品質ゲート付きにし、ゲートは**手動アンカーの対 GT 分布から事前規定**(データを見て決めない)
   - 「順序・疲労」行 → 手動アンカーを各セッションに散らし、再掲セッションのような外形の違う追加セッションは不要になる
   - 「サイドチャネル」行 → 提案を全条件オフラインで事前計算し配信(runtime に GPU 不要=待ち時間差が消える)
   - 「レシピの妥当性」行 → 条件間で学習手順を**変えない**(n によって epoch を変えると「実運用の手順そのもの」という主張が崩れる)
   - 「新規性」行 → 事前計算段階で「提案の修正量」など予測子となる特徴を JSON に同梱し、実測との相関を副次解析に据える
4. 表と仕様を計画ファイルに書いたうえで、コードレベルの実装計画は Plan サブエージェントに検証させる(設計と実装の分業)。

## 注意点・落とし穴
- 方針提示を受けて Claude 側で決めた項目は、**ユーザーが個別に承認したわけではない**。計画提示時に「表から導いて決めた項目」を
  明示列挙し(例: 1 epoch 統一、再掲セッション廃止、3 seed、105 枚/人)、そこで異論を受ける。
- 対策には必ずコストがある(seed 数 × 条件数 × 構造数のチェックポイント生成、被験者負荷)。右列に書いた対策の総コストを
  一度合算して、被験者 1 人あたり時間と GPU 時間で現実性を確認する。
- 既存 Knowledge の「開始前必須 / 後から補える」仕分け(pre-launch-paper-risk-triage)は**実施直前の棚卸し**、
  本パターンは**設計時に先回りして潰す**もの。両方を使うと、実施直前の表が短くなる。

## 追記 (2026-09-19)
- 出典: Experimental_record/20260919.md(「統計的な穴」の洗い出し)
- 「突っ込み → 対策」表は査読者の直感に合わせて書くため、**統計的には穴がある対策を採ってしまうことがある**。
  本プロジェクトでは「speed–accuracy」行の対策として入れた**品質ゲート付き主要評価**が、条件依存の不合格(選択バイアス)を生むため
  統計レビューで取り下げ、「全試行の時間(H1)+ 品質非劣性(H2)の fixed-sequence」に置き換えた。
  同じレビューで、10 スロット(手動 2/セッション)の Latin 長方形は 40% の画像に手動対照が付かないことも判明し、9 スロット・90 枚に戻した。
- 手順に 1 ステップ足す: **表 → 設計仕様 → 統計レビュー(主要評価のサブセット化・変量効果の水準数・画像内対照の有無・多重性・
  マージン根拠・検出力・分布・盲検検証)→ 確定 → 実装計画の委譲**。統計レビューを委譲の後に回すと、サブエージェントの報告と仕様が食い違う。
  詳細チェック項目は [[quality-gated-outcome-selection-bias-split-speed-and-quality]]。
