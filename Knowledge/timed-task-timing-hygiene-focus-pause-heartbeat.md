# 計時タスクのタイミング衛生: フォーカス喪失で一時停止 + 席外し監視 heartbeat
- type: technique
- created: 2026-07-12
- tags: [instrumentation, timing, human-study, webapp, metrics]

## 課題
所要時間(や単位時間あたりの操作量)を効率指標にする human study では、
「作業していない時間」が `duration` に混入すると条件間比較が歪む。ブラウザ計時では特に次の2つが汚染源になる:
1. **他 window/タブへ切替・最小化**: 作業を中断しているのにタイマーが回り続ける。復帰時にカーソルが飛ぶと移動距離も過大計上される。
2. **タブは開いたまま離席(トイレ等)**: フォーカスは外れないので上記では捕まらない。無操作が続くだけで、外形上は「作業中で手が遅い」と区別がつかない。

## 解決アプローチ
2つを別々の仕組みで捕まえる。片方だけでは不十分。

### ① フォーカス喪失で計測を一時停止(能動的除外)
- トリガは **`visibilitychange`(タブ切替/最小化)と `blur`/`focus`(他アプリへフォーカス移動)の両方**を張る。片方だと OS/ブラウザ差で漏れる。
- 非アクティブになった瞬間に **タイマー・全カウント・マウス移動距離の加算を止める**。タイマーは「アクティブ経過秒だけを積算」する方式にする(wall-clock 差分をそのまま使わない)。
- 非アクティブ経過は作業時間 `duration` から**除外**し、別カラム(`paused_time_sec`)に**記録は残す**(捨てない=後から異常検知に使える)。
- **復帰直後のカーソル飛びを移動距離に加算しないガード**を入れる(戻った瞬間の一手だけ mousemove を無視)。これが無いと「別画面から戻る」たびに巨大な移動距離が入る。
- **誤停止の防止**: 提出後アンケート中/保存中など「作業タイマーを止めている局面」(`timing=false`)ではフォーカスを外しても一時停止しない。フラグで区別する。
- UI にオーバーレイ(例「一時停止中」)を出して canvas をブロックすると、被験者にも状態が伝わり、非アクティブ中の誤操作も防げる。

### ② 席外し監視 heartbeat(受動的検出)
- アクティブ作業中は **一定間隔(例15秒)で `{t: アクティブ経過秒, wall: 実時刻ms}` を記録**(ロスレス層=JSONL に配列で蓄積、CSV には出さなくてよい)。
- **タブを開いたまま離席**すると①は発火しないが、heartbeat は打ち続ける一方で操作イベント(クリック・頂点編集等)が途切れる。この「heartbeat は生きているが操作が無い区間」= 席外し/思考停止として**後から検出**できる。
- 既存の `idle_time_sec`(操作間ギャップ合計)と併用すると、「PC 前にいて手が止まっている」と「そもそも席/画面を離れた」を切り分けられる。

## 実装メモ(本プロジェクト)
- `metrics.js`: `pause()`/`resume()`(アクティブ経過だけ積算)、復帰直後の mousemove ガード、heartbeat の start/stop と `heartbeats[]` 蓄積。
- `app.js`: 計測中フラグ `timing`、`visibilitychange`/`blur`/`focus` への配線、タイマー表示をアクティブ経過ベースへ、`_finishSession`/`abort` でのフラグクリア。
- `index.html`/`style.css`: `#pause-overlay`。
- `session.py`: `summary.csv` に `paused_time_sec` 列(heartbeat は JSONL のみ)。
- **注意**: CSV カラム追加(backend)は稼働中サーバへ即反映されない。フロントは no-cache で即反映されるが、**backend 変更後はサーバ再起動が必要**。

## 検証(何を測れば「効いている」と言えるか)
- 一時停止を挟んで `duration` がその分**短く**、`paused_time_sec` にその分が入る。
- 非アクティブ中の大きなカーソル移動が移動距離に**入らない**(復帰後の一手のみ計上)。
- アンケート/保存中(`timing=false`)のフォーカス喪失では**一時停止しない**。
- heartbeat が `{t, wall}` で JSONL に落ち、操作イベントと突き合わせできる。

## 更新 (2026-07-12)
- 出典: Experimental_record/20260712.md
- **提出後の後処理 UI の並び順もタイミング衛生の一部**。順序は「**提出(=タイマー停止) → 確認画面 → 主観評価 → 保存**」とし、
  タイマーは提出押下の瞬間に止める。これで確認レビュー・主観評価(Paas)の回答時間が `duration` に混入しない。
- 確認画面に「**修正する**」(提出取り消し→編集へ戻る)を置く場合は、**戻った位置から計測を再開**する。
  ただし修正で戻るまでの確認レビュー時間は `duration` 除外の実装次第で `paused_time_sec` に混入しうる
  (本プロジェクトでは少量混入を許容。厳密にするなら確認レビュー分の別枠カラムを設ける)。
