# 実験設計を別プロジェクトの案で置き換えるときは「凍結済み成果物」と「実装の継ぎ目」を先に棚卸しする

- type: pattern
- created: 2026-09-19
- tags: [experimental-design, pre-registration, user-study, refactoring, HITL, planning]

## 概要
事前登録・IRB・配布資料まで整えた被験者実験を、別プロジェクトの新知見(より良いモデル/新しい設計案)で
作り直したくなったとき、いきなり新設計を書き始めず、**(1) すでに凍結されていて取り消せないもの、
(2) 収集済みで埋没コストになるもの、(3) 既存実装のうち差し替え境界が閉じている部分**の 3 点を
先に列挙してから計画を立てる。

## 背景・発見経緯
2026-09-19、SegFormer-B1 × 8 データ量条件の HITL 実験(OSF 事前登録済み・アノテータ配布直前)を、
別プロジェクトで有効性が分かった「SAM decoder-LoRA の n-shot 用量反応・ランダム化」設計へ置き換える依頼を受けた。
現状調査で判明した前提:
- **OSF 事前登録は Submit 済みで取消不可**(設計変更は Update registration で改訂版を追加し逸脱を明記、または新規登録)
- **本番アノテーションは 0 件** → データの埋没コストは無く、置換の障壁は文書と登録のみ
- 推論バックエンドは `{channel: 512×512 uint8 mask}` の出力契約で閉じており、モデル差し替えは `inference.py` 1 ファイルに局所化できる
- 一方、条件数を変えると割付スクリプトの枚数・ブロック・Latin 方格・セッション数が全て連動して変わる
これらを先に押さえたことで、「どこまでが安く変えられ、どこからが登録の改訂を伴うか」が計画の骨格になった。

## 詳細
棚卸しの観点(ピボット前チェックリスト):
1. **凍結済み・取消不可**: 事前登録(OSF/UMIN 等)の登録内容とハッシュ、IRB 承認の範囲、公開済み DOI、配布済み資料
   → 変更するなら「改訂登録+逸脱明記」「新規登録」「範囲内確認」のどれかを計画に含める
2. **収集済みデータ**: 本番記録が 0 件なら設計を丸ごと置換できる。1 件でもあれば「旧設計データの扱い」を決める
3. **差し替え境界**: 既存実装で契約が閉じているモジュール(推論=マスク出力契約、記録=`experiment.json` 駆動)は
   そのまま流用し、連動して壊れる箇所(割付生成の条件数依存)を洗い出す
4. **参照文書のドリフト**: 別プロジェクトの設計メモはファイル名と中身が乖離していることがある
   (例: `study-design-crossover.md` の現行案は用量反応・ランダム化で、クロスオーバー案は旧案として保存)。
   冒頭の summary/updated を読み、ユーザーがどの版を指しているかをプラン提示時に確認する
5. **調査はサブエージェントに分業**: 「自プロジェクトの現状・制約」と「持ち込む側の資産」は別エージェントで並列に調べ、
   メインでは結果を突き合わせて計画だけを書く

## 適用場面
- 事前登録済み/倫理承認済みの被験者実験を、実施前に別モデル・別条件構造へ作り直すとき
- 別リポジトリの知見を既存の実験アプリに移植するとき(どのモジュール契約が保たれるかを先に確認)
- 「ファイル名 ≠ 現行内容」の設計メモを参照して依頼されたとき

## 追記 (2026-09-19)
- 関連: Experimental_record/20260919.md
「持ち込む側」(別プロジェクトのモデル資産)を棚卸しするときの追加観点。研究用リポジトリは
**指標を出すことが目的で、再利用可能な成果物(重み)を残していないことが多い**。few_shot_HITL の調査で判明した典型例:
- **重みが保存されていない**: 学習曲線実験は in-memory で学習→評価→破棄しており `torch.save` が一度も無かった。
  「精度が出た」≠「チェックポイントがある」。移植計画には**保存付きの学習スクリプト新設**を最初のタスクとして入れる
- **条件の端が未検証**: 学習器が「≥4 枚必須」のため n=1, 2 は一度も走っていない。設計で使う全条件が既存コードの
  前提(最小枚数・val 分割の有無)で動くかを確認する
- **分割方針の不一致**: 持ち込む側は患者層化ランダム(患者リークあり)、受け入れ側は患者分離が前提。
  学習順・評価・被験者用画像プールを受け入れ側の方針で組み直す作業を計画に含める
- **アプリの推論経路が最終モデルと違う**: 持ち込む側の annotation app は旧バックエンド(CNN head + 境界プロンプト)のままで、
  最終方針(decoder-LoRA)は未統合だった。「どのアプリを使うか」は最終モデルが載っている方で決める
- ユーザー確認は **1 回に 4 問は多い**: 前半 2 問(参照 GT・被験者数)は即答されたが、後半 2 問(学習レシピ・セッション構成)は
  「clarify したい」で保留された。設計構造に関わる問いは前提説明を添えて 1〜2 問ずつ出す

## 追記 (2026-09-19)
- 関連: Experimental_record/20260919.md(Plan エージェントの実装計画)
- 「分割方針の不一致」は**数で検証**する。持ち込む側(MODEL)の既存評価セット 200 枚は受け入れ側(STUDY)の被験者用 held-out プールと
  **18 患者 / 35 枚**を、既存学習順 128 枚は 25 枚分の患者を共有していた(いずれも患者 id = ファイル名先頭トークンで照合)。
  「患者層化ランダム」は「患者分離」ではないので、2 リポジトリを組み合わせるときは
  ①受け入れ側の被験者用画像を先に凍結(`study_images.json` + sha256)→ ②持ち込む側の評価セット・学習順をその患者を除外して再構成 →
  ③両リポで患者集合の互いに素を assert、の順に契約を張る。除外後に十分な患者数(本件 157 患者)が残るかも先に数える。
- 実装計画を委譲するなら、被験者実験の runtime からモデル依存(torch/transformers)を外し、提案を**事前計算 JSON**で配る構成にすると
  2 リポ間の契約が「入力画像リスト」と「提案 JSON」の 2 ファイル(+ sha)に閉じ、環境差(transformers 4.x/5.x)も無関係になる。
