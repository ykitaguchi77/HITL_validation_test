# HITLアノテーション効率研究の盲検化と交絡設計

- type: pattern
- created: 2026-06-16
- tags: [experimental-design, HITL, blinding, confound, bias]

## 要点
「モデル習熟度(学習データ量)がHITLアノテーション工数をどう変えるか」を測る研究では、
**アノテータがどの条件(モデル/フェーズ)を編集中か分かること自体が交絡源**になる。
評価の妥当性を脅かす3大要因と、その統制可否を分けて設計する。

## 適用場面 / 状況
- 複数の「初期予測の質が異なる条件」を1人(少数)のアノテータが順に編集し、所要時間・クリック・
  修正量などを比較する実験。
- 本プロジェクト: scratch + HITL@{500..2500}(将来 100/200/300 追加可)の各10枚を比較。

## 内容(設計原則)
1. **期待バイアスを盲検で除く**: 「弱いモデル/強いモデル」と分かると初期予測への信頼度=編集量が
   変わる。→ **モデル名を秘匿しランダム混合提示**(ブラインド)すれば除去でき、順序/疲労効果も分散。
2. **盲検化できる範囲を見極める**: **scratch(空キャンバス)は予測済みと見た目で区別でき盲検化不可能**。
   → 盲検化できるのは「予測ありの条件どうし(HITLモデル間)のみ=部分盲検」。scratch は識別可能な基準として混在。
3. **最大の残存脅威は「画像難易度の交絡」**: 盲検にしても、条件ごとに別画像(例: 各条件10枚)だと
   モデル効果が画像差に埋もれうる。対策:
   - アノテータ3名以上 → **ラテン方格**で画像↔条件割当を人ごとにローテーション(交絡を分離。改修やや大)。
   - 1名 → 交絡を受容し**限界として明記**。視線方向バランス(例 正面7+周辺3)で一部のみ統制。
4. **一般化の限界**: 単一アノテータはケーススタディ的。可能なら3名以上。
5. **実装的本命=ハイブリッド**: ツールに「ブラインド混合モード」(全画像シャッフル提示・初期予測の
   出所を非表示・条件は内部ログ・scratch は空表示)を追加。小UI追加でバイアス統制が得られる。
   デバッグ用に従来のノンブラインド(フェーズ別)も残す。
   → この判断がUI実装を分岐させる(ノンブラインド=ドロップダウン追加だけ / ブラインド=混合モード実装)。

## 注意点・落とし穴
- 「盲検にすれば妥当」ではない。**盲検は期待バイアスのみ**を除き、画像難易度交絡は別途設計が要る。
- 設計確定前にUIを作り込むと手戻りする。**盲検方式の決定 → UI実装**の順。
- 外部LLMにセカンドオピニオンを取る場合、`codex exec` は非gitディレクトリで `--skip-git-repo-check` が必要・
  認証切れ(401)で落ちることがある(`codex login`)。さらに **ChatGPT アカウント連携の Codex は利用可能モデルが
  限定的**(`gpt-5`・`gpt-5-codex` が非対応、`o4-mini` も 400 で失敗した事例あり)→ 相談前に使えるモデルの確定が要る。
  `gemini -p` は別系統(2.5-pro はクォータ枯渇しうる→ `flash` で代替可)。可用性に依存しすぎない。

## 更新 (2026-06-16)
- 上記推奨を **Gemini(flash)で相互検証** → Claude と 5論点すべて一致(ブラインド混合/scratch別建て/画像難易度交絡が
  残存脅威/ラテン方格/ハイブリッド)。設計の頑健性が高いことを確認。
- **ユーザー決定**: scratch は別建て基準・8つの HITL モデル間は盲検混合で確定。提示単位は **1セッション=10枚
  (正面7+周辺3)**。→ 実装はハイブリッド(ブラインド混合モード)方向で確定。
- 未確定(Q2): アノテータ人数・前向き(プロスペクティブ)化・パイロット要否・推奨解析(混合効果モデル等)。Codex 相談を継続。

## 更新 (2026-06-16, Q2 設計推奨)
盲検方式(上記)に続く Q2(人数・前向き化・パイロット・解析)について Claude の推奨を整理(Codex は
gpt-5/gpt-5-codex/o4-mini とも ChatGPTアカウント非対応・Gemini クォータ枯渇で外部意見未取得・ユーザー回答待ち)。
1. **前向き化=軽量に実施**: 確認試験ほど厳密でなくてよいが、人数・条件・主要アウトカム・解析法を**事前固定
   (短い解析計画書)**して p-hacking 回避。
2. **アノテータ 3〜5名(最低3)**: 被験者内反復測定で画像レベル観測数 N×90 と多く用量反応カーブは少人数でも検出可。
   律速はアノテータ間一般化(ランダム効果)。N=1=ケーススタディ、N=3 で再現主張可、N=5 で安定。
3. **専用パイロット不要→内部パイロット**: 1人目を内部パイロット化し動作確認/効果量把握を兼ね、**そのデータも本解析に
   組入れ**(プロトコル不変なら破棄不要)。新規HCI指標では事前検定力計算より内部実測が有用。
4. **解析=混合効果モデル** `outcome ~ 条件(or log学習枚数) + gaze + (1|アノテータ) + (1|画像)`。
   **画像をランダム効果に**して画像難易度の交絡を一部吸収。scratch vs HITL は別対比。

## 更新 (2026-06-18, 確定設計の実装)
上記原則を webapp に実装・確定(Q2 含む最終形)。具体化のポイント:
1. **3×9 Latin 方格**: アノテータ3名 × 9セッション(練習1 + scratch1 + HITL8)で条件提示順を均衡化。
   `scratch は全アノテータでセッション0固定`(別建て基準)、HITL 8条件(seg100..2500)はシャッフル interleave。
2. **隠し正解はサーバ側のみ**: API(`/api/run|session|predict|submit`)はモデル名/条件/ブロックをクライアントへ一切
   返さず、保存記録にのみサーバ側で付与(例 condition=seg300, train_size=300, block=B3)。フロントは盲検維持。
3. **練習セッション**: 5枚(正面3+周辺2、seg1000 で初期予測)、`is_practice=true` で解析除外・本番と画像非重複。
   **練習でのみ GT オーバーレイ + per-class Dice を表示**(操作習熟用)。本番は GT/Dice を完全非表示=期待バイアス除去。
4. **GT 作成者はアノテータから除外**(自分の正解を覚えている交絡を回避)。
5. **モデルキャッシュは提示モデル数に合わせる**(4→9): 8モデルの盲検混合でキャッシュ・スラッシングを避ける。
6. 解析カラムを記録に追加: annotator, condition, model, train_size, block, gaze, is_practice, session_index 等
   → そのまま混合効果モデル `outcome ~ log(train_size) + gaze + (1|annotator) + (1|image)` に投入可能。
- 残注意: predict 結果を事前計算/キャッシュしないと**応答時間がモデル毎に差→タイミング・サイドチャネル**で盲検が
  漏れうる(推奨対策・未実装)。外部 LLM 照会は Codix(401/モデル非対応)・Gemini(429)で結局取得できず、判断は自前分析。

## 更新 (2026-06-18, 練習2部構成 + 動作テスト用アノテータ)
運用直前の2つの設計改良:
1. **練習は本番に現れる全ワークフローを必ずカバーする**: 本番が scratch(ゼロ描画)と HITL(予測修正)の
   2系統なので、練習も **練習1「Scratch」+ 練習2「修正(seg1000)」** の2セッションに分割(各 正面2+周辺1=3枚、
   周辺視を入れて iris/pupil 楕円の傾き編集も練習)。**提出ごとに GT を表示**(解析除外)。片方しか練習しないと
   習熟差が条件効果に交絡するため、両アームを事前に均等練習させる。
2. **リハーサル用の擬似アノテータでデータを汚さない**: UI に `test`(「動作テスト用(本番に含めない)」)を追加。
   割当は実アノテータ1と同一だが、記録だけ `outputs/results/test_*/`(annotator="test")へ**別経路で保存**。
   実験者の動作確認が本解析データに混入しないようにする。解析時は **annotator!="test" かつ is_practice==false** で絞る。
