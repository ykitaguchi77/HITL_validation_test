# CVAT風HITLアノーテーションwebappの実装知見（FastAPI + Konva.js）

- type: technique
- created: 2026-06-15
- tags: [webapp, annotation, HITL, konva, fastapi, segformer]

## 概要
眼瞼セグメンテーションのHITLアノテーション計測webappを実装した際の、再利用可能な技術知見。
ビルド不要（CDN Konva.js）＋ FastAPI推論バックエンドという軽量構成で、CVAT風の
polygon/楕円OBB編集と詳細な操作計測を実現する方法。

## 背景・発見経緯
`scripts/webapp/` を新規実装する中で得た、座標系・モデル接続・UI操作・検証手法の要点。

## 詳細

### モデル接続（SegFormer amodal → 編集可能ベクタ）
- SegFormer-B1 amodal は **3ch独立sigmoid**（eyelid=Eyelid+Caruncle統合 / iris / pupil）。
  argmaxではなくch毎に閾値0.5。Caruncleは独立予測されない。
- ロード: `from_pretrained(backbone, num_labels=3, ignore_mismatched_sizes=True)` →
  `load_state_dict(ckpt["model"])`。head MISMATCH警告は正常（学習済みheadで上書きされる）。
- 推論は512×512固定。マスク→編集ベクタ変換: eyelid は `findContours`+`approxPolyDP` でポリゴン、
  iris/pupil は `fitEllipse` で OBB(cx,cy,rx,ry,rotation)。**native画像座標へスケール戻し**が必須
  （表示はnative解像度、推論は512）。

### 座標系の一貫性
- 図形ジオメトリは全て**画像native画素座標**で保持・保存・採点（GTのCVAT XMLもnative座標）。
- Konvaは world(Group) を scale/position し、画像と図形を同Groupの子にして一緒に変換。
  アンカー/ストロークは `size/view.scale` で画面上一定サイズに保つ。
- マウス移動距離などの計測は画面pxでなく**画像座標**で積算（ズーム非依存）。

### Konva UI 実装の要点
- ポリゴン: 頂点アンカー（draggable Circle, `name:"vertex"`）＋辺中点（挿入用）。
  アンカーは中点より**最前面**に（`moveToTop`）。さもないと重なり時に始点等が掴めない。
- 中点クリック挿入→**同一ジェスチャで `anchor.startDrag()`** すると挿入直後に位置調整できる。
- 楕円OBB: `Konva.Transformer`（回転可）。transform後は scale を radius に bake してデータを正規化。
- click-vs-drag分離: mousedownで即動作せず press を記録し、移動4px超で drag(=背景ならパン)、
  非移動なら click動作（点追加/選択解除）。これで「背景ドラッグでパン」と描画が両立。
- タッチ: container に `touch-action:none`、touchstart/move/end を自前処理で1本指パン・2本指ピンチ。
- undo/redo: 図形全体を `{classKey,kind,data}` でシリアライズしたスナップショット履歴が単純で堅牢。

### 検証手法（重要）
- **Playwrightの合成 Mouse/PointerEvent は Konva のポインタ処理に届かない**（描画/パンが発火しない）。
  → アプリ本体を `window.HITL.app` で公開し、`stage.getPointerPosition` を上書きして
  コントローラの `_down/_move/_up` を直接駆動して単体検証する。
- バックエンドは GT を「提出」として round-trip させ Dice=1.000 を確認すると採点系の正当性が取れる。

### データ取り扱い
- `image_metadata.csv` は系統A（ids 0-1999）限定。test範囲(2500-2999)は **XMLから直接**取得する。
- 症例リーク回避: patient_id = ファイル名先頭（最初の`-`前）。test症例は「全アノ画像のmin id ≥ 2500」で抽出。

## 適用場面
- HITL/active-learning のアノテーション効率を計測するUIを自作するとき。
- セグメンテーションモデル出力を編集可能なベクタ初期値として提示するHITLパイプライン。
- Konvaでズーム/パン＋頂点編集のCVAT風エディタを軽量に作るとき。

## 追記 (2026-06-15) — ドラッグ判定と Transformer の要点
- 関連: Experimental_record/20260615.md

### 「掴んだ対象」でドラッグ意図を分岐する
- 図形の塗り(`fill`)が画像を覆うUIでは「背景ドラッグでパン」は破綻する（掴んだ点が
  図形本体になりパンが阻害される）。判定を「背景か否か」ではなく
  **「選択中図形の編集ハンドルを掴んだか否か」**にする:
  - 選択ポリゴンの頂点 / 選択楕円の本体を掴んだ時 → 編集（Konva に委譲）
  - それ以外（空白・非選択図形の上を含む）→ 常にパン
- 選択は mousedown では行わず press を保留し、**クリック（非ドラッグ）時のみ**選択/解除する。
  これで「未選択なら画像のどこを掴んでもパン」「選択中はハンドルで編集」が両立する。

### Konva.Transformer をパン/選択ロジックと共存させる
- Transformer のアンカー/回転ハンドルは `name:"vertex"` でも shape 本体でもないため、
  自前の mousedown 処理が**パンに化けてリサイズ/回転を奪う**。
  対策: `e.target.getParent() instanceof Konva.Transformer` なら自前処理を return し Konva に委譲。
- **ハンドルサイズをズーム非依存にするなら Transformer は world(スケールGroup)でなく
  layer(非スケール)に置く**。`anchorSize`/`rotateAnchorOffset`/枠線幅を画面px定数で設定でき、
  毎ズームの `size/scale` 補正が不要。ノード追従は `transformer.forceUpdate()`。
  （world 内に置いて `/scale` で打ち消す方式は再計算タイミングでサイズがブレる）
- 検証: ヘッドレス Playwright で実 `canvas.js`/`tools.js` を `python -m http.server` 配信し、
  既存ブラウザ占有時は `chromium_headless_shell` を `executablePath` 直指定して駆動。

## 追記 (2026-06-15) — 点追加(extend)モード・塗り切替・イベント順序

### 既存ポリゴンへの「点追加(統合)モード」
- 「新しい図形を作る」のではなく**選択中の既存ポリゴンの頂点列に点を追記**するモード。
  起動条件をポリゴン**選択中のみ**に絞ると、未選択時に誤って図形が生まれるのを防げる。
- 確定(dblclick/Enter)後も同じ図形を選択・編集可能に保ち、Esc は追加分だけ破棄して原形へ戻す
  （開始時の頂点数を覚えておき差分を切り詰める）。

### setEditable(false) は頂点の丸を消す → 編集中は自前マーカー
- 編集ハンドルを隠す目的で `setEditable(false)` すると**頂点アンカーの丸が全消え**し、
  点を置いている最中に位置が見えない。描画ツール同様、モード中は各頂点に丸マーカーを
  自前生成し、追加のたびに足す。確定/取消で破棄して実アンカーへ戻す。ズーム時は画面px一定にリスケール。

### dblclick と mouseup の発火順序に依存しない
- Playwright（実ブラウザでも環境差あり）は `dblclick` を2つ目の `mouseup` の**前**に発火し得る
  （`down1,up1,down2,dbl,up2`）。確定を `dbl` で行うと、後続の `up2` が確定後に走って
  選択解除などの副作用を起こす。`_dbl` でワンショットフラグを立て**次の `_down` でクリア**すると、
  「dbl 直後の up を1回だけ無視」でき、実ブラウザの順序とも両立する。

### 塗りつぶし表示と当たり判定(hit)の分離
- 「塗りの見た目ON/OFF」を**当たり判定を壊さずに**切替えるには、`fill` の **alpha だけ 0** にし
  `hasFill`(Konva の `fill` 指定自体)は残す。塗りOFFでも内部クリックで図形を選択できる。
  状態は `view.showFill` に保持し画像切替後も維持、OFF中に作る新規図形も透明で生成する。
  マスクの表示/非表示（クラス別 visibility）とは独立したトグルとして実装する。

## 追記 (2026-06-16) — 点追加のエッジ挿入・クラス連動・キー操作
- 関連: Experimental_record/20260616.md

### 点追加は「末尾追記」でなく「最近接エッジへ挿入」
- extendモードで新点を頂点列の**末尾に追記**すると、遠く離れた点同士が線で結ばれて図形が破綻する。
  正しくは**新点に最も近い既存エッジ(線分)を求め、その2頂点の間に挿入**する。
  これで「もとのエリアを自然に広げる」結ばれ方になる(中点挿入と同じ発想を任意クリック点へ拡張)。

### クラスボタンと選択状態の連動
- 図形がアクティブな状態で別クラスボタンを押したら、現在図形を非アクティブ化して
  **即その新クラスのアノテーションへ移れる**ようにする(クラス切替=確定+モード切替)。
- 「1クラス=基本1図形」運用では、**クラス選択時に既存の同クラス図形があれば自動でactive**にすると、
  新規作成と再編集が1操作で済む。

### キーボード操作(点打ち/微調整)とフィット
- マウスクリックに加え**スペースキーでも点を設置**(マウスを動かさず連打しやすい)。
- 図形選択中の**矢印キーで画像座標1px移動**(ポリゴンは全頂点・楕円は中心)。
  キーリピート中の連続移動は**離した時に1回だけコミット**(=1 undo)、未選択時は無反応。
- 画像をビューポートに最大化する**フィットボタン**(scale/positionをbboxに合わせて再計算)。

## 追記 (2026-06-16) — フェーズ系は完全 config 駆動
- 関連: Experimental_record/20260616.md
- 実験フェーズ(scratch / HITL@N)は **`experiment.json` 起点で完全に config 駆動**。フロント(`app.js`)に
  フェーズ数・1フェーズ枚数のハードコードは無く、**フェーズを追加すればセットアップ画面のドロップダウンに
  自動反映**される。`prepare_experiment.py` も `len(PHASES)` で枚数を自動スケールするため、**フェーズ追加は
  生成スクリプトの再実行だけで完了**(コード改修不要、UIは自動反映)。
- 含意: 「フェーズ/モデルを増やす」変更は安価。逆に**提示方法を変える(例: ブラインド混合提示)場合のみ**
  フロントに新モードの実装が要る(config だけでは表現できないUI挙動だから)。

## 追記 (2026-06-18) — 重なり部の編集・選択UI・プレフィル密度
- 関連: Experimental_record/20260618.md

### 重なるクラスの「選択中だけ最前面化」で重なり部を編集可能に
- 複数クラスのポリゴン/楕円が重なると、上に積まれたクラスのアンカーが下のクラスの頂点操作を奪う。
- 選択時に `group.moveToTop()` で**そのクラスだけ最前面**へ持ち上げ、画像レイヤは常に最背面を維持する。
  これで「eyelid を選んでいる間は iris/pupil と重なる部分でも eyelid 頂点をドラッグできる」。

### クラス選択は「サイドバー(右タブ)のみ・canvasクリックでは選択しない」
- canvas クリックで選択が変わると、頂点ドラッグ中に隣の図形へ選択が飛ぶ事故が起きる。
- canvas の選択切替を無効化(`selected=null` 維持)し、**選択はサイドバーのクラスボタン経由のみ**にすると操作が安定する。

### プレフィルの点密度は `mask_to_polygon` の近似 eps で制御
- 推論マスク→ポリゴン化(`cv2.approxPolyDP` 系)の **eps を下げると点数が増える**(例 eps 0.004→0.0015 で eyelid 16→38点、約2.4倍)。
  点が多いほど「間を埋める」手作業が減るが、頂点編集の手数とトレードオフ。実アノテーションの体感で調整する。

### クラスを1つ廃止するときの波及
- あるクラス(例 caruncle)を廃止して別クラスへ統合する場合、**GT 読込(統合)・クラス定義/ラベルマップ(`config.py`)・
  prefill/GT 描画(`app.js`)を可変クラス数に対応**させる。`experiment.json` はクラス情報を持たないので再生成は不要。
  フロントの `getAnnotation` が廃止クラスの空キーを残しても backend が無視すれば無害(クラッシュ回避)。

## 追記 (2026-06-18) — プレフィル「均等化」と「直したのに直らない」=配信キャッシュ
- 関連: Experimental_record/20260618.md

### プレフィルの点を「均等」にするなら eps 調整でなく等弧長リサンプリング
- `cv2.approxPolyDP`(曲率ベース)は **eps を下げれば点数は増える**が、曲率の高い所に点が偏り**間隔が不均等**になる。
  「点を均等に」したい場合は eps いじりでは要件を満たさない。
- 正攻法は**輪郭を等弧長で再サンプリング**(累積弧長を一定間隔=例14pxで分割して点を取る)。
  eyelid prefill が約58点・**間隔ほぼ一定(spacing std ≈1.1px)**になり、「間を埋める」手作業が均等に減る。
- 上の (2026-06-18) eps 制御の記述は「点数」を増やす手段。「等間隔」が要件なら等弧長リサンプリングへ置換するのが正解。

### フロント修正が「直したのに直らない」報告 → まず配信キャッシュを疑う
- 静的 JS/CSS を直しても、ユーザーのブラウザが**旧アセットをキャッシュ**していると修正が反映されず
  「症状が改善されない」と報告され続ける(コードは正しいのに無限に追加修正してしまう罠)。
- 切り分け: **Playwright/シークレットウィンドウ(キャッシュ非依存)で現行コードの挙動を機械確認**し、
  正しければ原因は配信側。開発配信では静的アセットに **`Cache-Control: no-cache`** を付け、
  ユーザーには一度だけハードリロード(Ctrl+F5)を依頼する。
- **再発 (2026-07-13)**: 「校正モードでマスクが2つずつ生成される」報告も同型と当初判断。バックエンド `/api/predict`(1クラス1形状)・
  Konva シーングラフ・全操作経路を機械検証したが**現行コードで一切再現せず**(1/1/1)。この種の切り分けでは
  **「そもそもユーザーのサーバが更新後コードで動いているか」も必ず確認**する(この時ユーザーの 8000 番は停止していた)。
  なお練習校正(p_hitl)の確認画面で実線+GT点線が重なるのは**仕様どおりの正当な二重輪郭**で、これを重複と誤認しないこと。
  **→ 後日談: この件はキャッシュではなく実バグだった**(セッション開始ボタンのダブルクリック競合。下記 2026-07-13 追記を参照)。
  「キャッシュ説」で片付ける前に、**サイドバーのカウント等データ構造由来の証拠**と**せっかちなユーザー操作(連打)の再現**を必ず確認する。

## 追記 (2026-06-18) — Konva 画像フィルタ(明るさ/コントラスト)と GT 統合外形
- 関連: Experimental_record/20260618.md

### Konva の Brighten/Contrast フィルタは「cache() してから」適用・画像差し替え毎に再適用
- `Konva.Filters.Brighten`/`Contrast` は **適用前に対象ノードを `node.cache()`** しないと効かない。
  手順: `imageNode.cache()` → `imageNode.filters([Konva.Filters.Brighten, Konva.Filters.Contrast])` →
  `imageNode.brightness(v)` / `imageNode.contrast(v)` → `layer.batchDraw()`。
- 値は **ビュー状態(`view.brightness/contrast`)として保持**し、画像を差し替えるたびに
  `cache()` + filters + 保持値の再適用を行う(さもないと新しい画像でフィルタが外れる)。
- 範囲: brightness は `[-1,1]`、contrast は `[-100,100]`(Konva フィルタの想定レンジ)。

### 「内部境界を消す」=隣接クラスを統合した外形1本で描く
- GT を Eyelid と Caruncle の2ポリゴンで別々に描くと**内部境界線が見えてしまう**。
  モデルの eyelid プレフィルと同様、**union(統合)した外形1本**で描けば内部境界が消える
  (shapely 等で union → 外形輪郭を等弧長リサンプリングして単一ポリゴンに)。表示の一貫性も取れる。

## 追記 (2026-06-18) — プレフィルの遅延ポップイン対策(ウォームアップ + 入力ブロック + 計測タイマー)
- 関連: Experimental_record/20260618.md

### 初回推論のコールドロードで GT が「入力途中に遅れて出る」→ 3点セットで解消
- 症状: 1例目だけモデルがコールドロード(初回推論で重み読込・初期化に数秒)するため、
  ユーザーが編集を始めた後にプレフィル/GT が遅れて描画され、**入力途中に GT がポップイン**してしまう。
- 対策(HITL アノテ webapp の定番3点):
  1. **入力ブロックのローディングオーバーレイ** — canvas を覆う `#loading-overlay`(z-index 30、
     「推論中… しばらくお待ちください」)を**画像ロード + プレフィル取得が揃うまで表示**し、揃ってから解除。
     途中ポップインと割り込み入力を防ぐ。
  2. **起動時モデル事前ウォームアップ** — サーバ起動時にダミー推論を走らせる(daemon thread で
     `_warm_models()`)。アノテータ選択→セッション開始の操作中(数十秒)に裏でロードが終わり、
     1例目から高速(検証: warm predict 0.07〜0.17秒、コールド数秒を解消)。
  3. **計測タイマーは準備完了後に開始** — 画像 + プレフィルが揃った後に `metrics.reset()` →
     overlay 解除 → タイマー開始の順にし、**推論/画像ロードの待ち時間を作業時間(duration)に含めない**。
     これをやらないと「効率」指標にロード待ちが混入して妥当性を損なう。
- 代替: 「割り当てが固定なら推論結果を事前計算して即出す」も有効(将来のタイミング・サイドチャネル対策と
  兼ねられる)。ただしウォームアップ + オーバーレイだけでも体感遅延と入力割り込みの双方を解消できる。

## 追記 (2026-07-12) — scratch の頂点計上漏れ・矩形(marquee)複数頂点選択+まとめて移動
- 関連: Experimental_record/20260712.md

### ゼロ描画(scratch)と点追加(extend)で頂点計上を「対称」に仕込む
- HITL(既存ポリゴンへの点追加=extend)は点を置くたびに `metrics.vertexAdded()` を呼んでいたのに、
  **ゼロから点を打つ scratch 描画(`_polyClick`)が呼び忘れ**ていて、scratch のみ `vertices_added=0` に
  なっていた。効率比較(scratch vs HITL の頂点編集労力)は**両パスで同じ計測を対称に仕込まないと成立しない**。
  新規描画パスと修正パスの両方で同じ metrics を呼ぶことをチェックリスト化する。

### Ctrl+ドラッグの矩形(marquee)で複数頂点を選択→まとめて移動
- 単一頂点ドラッグしか無い CVAT 風エディタに複数頂点編集を足すときの設計:
  - **選択スコープは「選択中の1ポリゴンの頂点のみ」**が実務的(眼瞼は基本1本を編集)。矩形内に隣クラス
    (虹彩/瞳孔)の頂点が入っても無視する。全図形を拾う方式は誤爆と実装複雑度が増して割に合わない。
  - トリガは **Ctrl+ドラッグ**(Shift=点追加、Space=点打ち、背景ドラッグ=パンで既に埋まっているため Ctrl が空く)。
  - `PolygonShape` 側に「選択頂点インデックス集合 + ハイライト + まとめて移動メソッド」を持たせ、
    `ToolController` 側で marquee 矩形・グループドラッグ・矢印キー微調整・Esc 解除・**1ジェスチャ=1 undo**・
    ツール切替時の marquee 掃除を配線する。移動頂点数ぶん `vertices_moved` を計上。
- **検証の注意**: undo は `restore()` で図形オブジェクトを再構築して選択解除するため、**undo 前に掴んだ
  shape 参照は破棄される**。Playwright 検証では undo 後に図形を読み直し・再選択してから形状を確認する
  (古い参照のまま assert すると stale reference で誤検知する)。

## 追記 (2026-07-13) — 「マスクが2つずつ」の真因=開始ボタンのダブルクリック競合(再入ガード3点セット)
- 関連: Experimental_record/20260713.md

### 症状と切り分けの反省
- 「校正モードでマスクが2つずつ生成される」報告を、前例(6/18)に倣い旧JSキャッシュ説で切り分けたが誤り。
  スクリーンショットで**サイドバーのカウント自体が 2**(=見た目でなく shapes 配列に2つずつ実在)、かつ最新機能が
  画面に出ていた(=JSは最新)ことで実バグと確定した。
- **教訓1**: 「機械検証で再現せず」を結論にする前に、**データ構造由来の証拠(カウント/配列長)**の有無と、
  **せっかちなユーザー操作(ボタン連打・ダブルクリック)**の再現を必ず試す。自分の再現手順(丁寧な単発クリック)は
  実ユーザーの操作分布を代表しない。

### 真因: async な開始処理中もボタンが生きているレース
- `startSession` が `/api/session` を `await` する間、**セッション一覧ボタンが表示・有効のまま**だった。
  素早い2回目のクリックで `startSession` が2並行 → `loadCurrent` → predict → 初期描画が2回走り、
  **1クラスにつき図形が2つ**生成される。Playwright のダブルクリック模擬で eyelid:2/iris:2/pupil:2 を完全再現。

### 修正パターン(再入ガード3点セット・フロントのみ)
1. **再入フラグ**(`_starting`): 処理中の再クリックを早期 return。`try/finally` で必ずリセット。
2. **UIを await 前に隠す/無効化**: 2回目のクリックが物理的に当たらないようにする(フラグだけに頼らない)。
3. **ロード世代ガード**(`_loadSeq` カウンタ): ロード開始時に世代を取り、描画直前に世代が変わっていたら中断。
   万一並行ロードが起きても古い方が描画しない多重防御。
- 検証はダブル/トリプルクリック+通常フロー(提出→確認→負担度→次へ)の両方を機械確認。
  フロントのみの修正は**サーバ再起動不要・ハードリロードで反映**とユーザーへ案内できる。
