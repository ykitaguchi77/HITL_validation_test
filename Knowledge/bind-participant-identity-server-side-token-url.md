# ユーザースタディの参加者 ID は「選ばせる」のではなくサーバ側で束縛する(個人トークン URL + サーバ側完了判定)
- type: pattern
- created: 2026-10-10
- tags: [user-study, webapp, participant-id, latin-square, data-integrity]

## 概要
共通パスワード + ID プルダウン + localStorage の完了管理という構成では、参加者が他人の ID を選んでも誰も気づかない。
個人専用のトークン付き URL で ID をサーバが決め、完了状況もサーバ側の保存記録から判定することで、取り違えと重複を入口で防ぐ。

## 背景・きっかけ
本番開始直前に「他人の ID でやってしまわないか」を点検したところ、
(1) ID は全員分のプルダウンから選択、(2) Basic 認証は全員共通、(3) 初期値が `test`、
(4) 完了状況はブラウザ localStorage のみ、という状態で、他人の Session 1 から問題なく開始できてしまうことが判明した。

## 詳細
- 被害の性質: 画像は全員共通で「画像×条件の割付」だけが参加者ごとに違う設計では、ID 取り違え = 割付の取り違え。
  Latin 方格/均衡割付が崩れ、本人の分と重複データが生じる(しかも見た目では検出しにくい)。
- 初期値を `test` にしておくと、切り替え忘れが「本番から外れる」形で静かに起きる。
- 対策の優先順:
  1. 個人トークン URL(`/?t=<random>`)→ サーバがトークン→ID を解決、本番ではプルダウン非表示。
  2. サーバ側完了判定(結果ディレクトリの記録から ID×セッション完了を判定し、完了済みは開始拒否)。localStorage 依存だと端末・ブラウザを変えた時の重複も防げない。
  3. 開始前の本人確認画面と作業中の名前常時表示(軽いが、うっかりにしか効かない)。
  4. 運用: 初回立ち会い、リンクの個別送付、仮 ID(annotator4 等)を早めに確定。
- テスト用 ID(`test` 等)は従来どおり自由に使える逃げ道を残す。

## 適用場面
- 共有 URL で配布する Web 型のアノテーション/リーダースタディ全般、特に参加者ごとに割付が異なる設計。
- 本番開始前チェックリスト(参加者ウォークスルーと同時に確認)。

## 追記 (2026-10-10)
- 出典: Experimental_record/20261010.md
実装して実サーバ + Playwright で検証した際の要点:
- **ident を 1 箇所で解決して全 API に適用**する(`test` or トークン → 名前、未知は 403)。入口画面だけ守っても、submit/abort など書込・削除系 API が名前を直接受け取ると他人名義で書けてしまう。session_id の名義と ident の一致も検証する。練習用アイテムなど「早期 return する分岐」も検証漏れしやすいので冒頭でチェック。
- 保存データの `annotator` 欄はトークンではなく**名前で保存**(トークンは認証用の秘密、解析キーは名前)。トークンファイルは git 管理外に置き、生成スクリプトは**再実行してもトークン不変**(リンクの再配布だけで済む)。ベース URL が変わる環境(trycloudflare)では URL を引数にしてリンクを再出力し、リンクなしで開いても個人コードを入力すれば入れる逃げ道を作る。
- サーバ側完了判定は「全画像提出済みのみ完了」とし、途中で止めたものは未完了扱い。
- 「完了済みは再開不可」は既存の運用判断(やり直し機能を予備手段として残す)と衝突しうる。実装前に過去の決定を grep して確認し、変えた点はユーザーに明示する。
- 検証は稼働中の本番ポートを避けて別ポートで起動し、検証データはアプリ自身の削除 API で片付ける(`rm -rf` はフックで拒否されることがある)。

## 追記 (2026-10-10)
- 出典: Experimental_record/20261010.md
- 配布用リンクの一覧メモ(例: リポジトリ直下 `annotator_links.md`)も**トークンと同格の資格情報**(開けばその人として記録できる)。作成したら即 `.gitignore` に追加し `git check-ignore -v` で除外を確認する。メモには公開 URL の起動日と再生成コマンドを書き、URL が変わる運用(trycloudflare)でも迷わないようにする。
- サーバ再起動後は、API でトークン解決とプルダウン候補(`test` のみ)を確認してから配布する。公開 URL 経由での表示確認は配布前に運用者自身が 1 回行う。
