# 必須クラス制約は導入前に実データ全体で成立を検証する

- type: lesson
- created: 2026-07-12
- tags: [annotation, data-hygiene, validation, blinding, medical]

## 教訓
アノテーション UI に「全クラス揃っていないと提出できない」ような**必須制約(バリデーション)を足すときは、実装だけで終わらせず、その制約が対象データの全画像で本当に成立するかを GT で機械検査する**。臨床画像では「そのクラスが解剖学的に存在しない/見えない」正常な症例がありうるため、制約が正当なアノテーションを弾く事故になる。

## 問題の背景
眼瞼・虹彩・瞳孔セグメンテーションの HITL webapp で、提出時に3クラス(Eyelid/Iris/Pupil)未完成ならブロックするガードを追加した。しかし**眼瞼下垂で瞳孔が完全に隠れている症例**では瞳孔が描けず、この制約が正当な提出を弾く恐れがあった。

## 検査でわかったこと
- **実験で使う96画像(本番90+練習6)・候補プール463枚はいずれも瞳孔欠損ゼロ** → 3クラス必須は安全。
- 一方**データセット全体(iris 注釈4467枚)では約34%(1504枚)が瞳孔なし**、うち8枚が「虹彩は見えるが瞳孔は隠れた」部分隠蔽(眼瞼下垂に典型)。
- これら隠れ瞳孔症例は**画像ID範囲(2500–2999)・患者分離・虹彩ありという実験プールの絞り込みで自然に排除**されていた(意図せず安全側だった)。

## 応用
- 必須制約を入れる前に「制約を満たさない画像が対象集合に0枚か」を GT で数える(`geometry.get_gt_annotation` などで在否確認)。実験プールだけでなく**再生成のもとになる候補プール**も検査する(別シード再生成で混入しないか)。
- プールの絞り込みが「たまたま」安全にしている場合は、明示フィルタ(例: プール構築に "pupil も必須" の1行)を足しておくと将来のデータ/ID範囲変更に対する保険になる。ただし既存割当を変えないこと([[seeded-design-additive-change-dedicated-rng]] と同じ発想)。
- 盲検実験では GT を検査に使ってもクライアントに出さないこと(本番画像への GT 取得は 403 で拒否)。
