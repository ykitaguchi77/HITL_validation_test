# ローカル配信の SPA を修正しても開きっぱなしのタブは古い JS を実行し続ける — 「修正の所在」で切り分け、節目に app_version を照合して自動リロードする
- type: lesson
- created: 2026-09-20
- tags: [webapp, spa, deployment, cache, user-study, instrumentation, verification, fastapi]

## 概要
ビルド無しの SPA(静的 JS を FastAPI が配信)を運用中に修正してサーバを再起動しても、
**ユーザーが開きっぱなしにしているタブは古い JS のまま動き続ける**。修正後の実データに同じ症状が再出現したとき、
「修正が効いていない」と「修正がクライアントに届いていない」を混同しやすい。
**backend 側の修正とフロント側の修正のどちらが効いているか**で切り分け、再発防止としてサーバが配る `app_version` を
クライアントが**セッション開始などの節目**で照合し、不一致なら自動リロードする。

## 背景・発見経緯
HITL 被験者実験 webapp のユーザー試用(2026-09-20)。Session 1 の実データ監査で計測バグ 2 件
(①フロント `app.js`: 既定クラスへの帰属漏れ、②backend `main.py`: 手動画像の `correction_dice=0`)を直してサーバを再起動した。
Session 2 の実データでは ②は反映(NaN)されていたのに、①の症状(`vertices_added=59` なのに `eyelid_vertices_added=0`)が最終行で再発。
コードを疑う前に「サーバ側だけ効いてフロント側だけ効いていない」という非対称に気づき、ユーザーのタブがリロードされていない
(サーバ再起動をまたいで同じページを使い続けていた)と特定した。

## 詳細
1. **切り分け**: 修正が複数あるなら、それぞれの所在(サーバ / クライアント)を表にし、実データで「効いた / 効かない」を照合する。
   サーバ側だけ効いている = クライアントが古い。両方効かない = 提出先が旧サーバ、または修正自体が誤り。
2. **検出の仕組み**(今回の実装):
   - backend: 起動時に static 配下の最新 mtime を `APP_VERSION` にして `/api/config` に載せる(ビルド番号が無いプロジェクト向けの最小実装)。
   - frontend: ページ読込時の `config.app_version` を保持し、**セッション開始時**に `/api/config` を再取得して比較。
     不一致なら alert → `location.reload()`(通信失敗時は best-effort でスキップ)。
   - 作業中(画像を編集している最中)には照合しない — 強制リロードは作業データを失うので、節目に限定する。
3. **運用**: 修正後は「一度 F5 してから次のセッションを」とユーザーに明示する。自動照合は保険であって、手順から外さない。
4. **記録の扱い**: 古いクライアントで記録された行は「計測バグあり」として扱い、解析対象なら除外・再取得の判断を記録する
   (今回は解析除外の test アカウントだったので実害なし)。

## 適用場面
- 静的ファイルを自前サーバから配る SPA を、被験者・共同研究者が**タブを開きっぱなし**で使う状況(ローカル/トンネル配信のユーザースタディ、社内ツール)。
- 修正後の実データで「直したはずのバグ」が再発したとき(まずクライアントの鮮度を疑う)。
- ビルドパイプラインが無く、キャッシュバスティングやサービスワーカーを導入するほどではない小規模 webapp。
