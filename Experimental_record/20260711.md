- 対象: interactive segmentation / AI-assisted annotation / HITL labeling の効率評価論文・ベンチマーク(医学系 radiology/ophthalmology + HCI系 CHI 等の両方)。

### 調査結果(既報と比べた欠落は5系統・いずれも後付け可能)
現在の計測は客観的操作ログ(時間・クリック・マウス移動・頂点/図形編集・undo/redo・zoom/pan)と重なり品質(Dice/IoU・correction Dice・面積変化)ではむしろ標準以上に充実。欠けているのは主に以下:

1. **主観的作業負荷(最優先)** — NASA-TLX(6下位尺度・加重版は15対比較)と SUS(10項目)。MONet(Asad et al., MICCAI 2023)は加重 NASA-TLX で作業負荷 24.67% 削減を主指標に。SW-FastEdit(2023)・Vision6D(2025, 11名)でも使用。Budd/Kainz サーベイ(Medical Image Analysis 71, 2021)は「時間**と**精神的努力」が HITL 評価の2大量と明言 → 現状は前者のみ。条件後の短フォームで最も安価に埋まる。
2. **境界距離の品質指標** — HD95・ASSD・Surface Dice at tolerance。MONet は Dice+ASSD、MICCAI 2025 SAMUSA 査読者が Hausdorff 追加を明示推奨。**注意**: 元は3Dボクセル物理間隔前提 → 2D はピクセル許容幅への読替が必要。**保存済みポリゴンからオフライン計算でき UI 変更不要**。
3. **アノテータ間/内の一致度** — ICC・読影者間ペアワイズ Dice・test-retest。IJCARS 2024 は ICC(手動0.80 vs AI支援0.84)、Vision6D は 11名×10サンプル×ランダム順3回で個人間・個人内を定量化。**一部画像を複数回/複数人に反復アノテートする設計が必要でコスト高**(ユーザーが挙げた既知ギャップに直接対応)。
4. **品質正規化した労力** — NoC@IoU(目標 IoU 到達クリック数)。RClicks(NeurIPS 2024)が NoC20@90 を定義、中心クリック仮定は実労力を 5〜29% 過小評価・ユーザー間で時間 3〜79% 変動。**注意**: シミュレートクリック前提でポリゴン頂点修正には翻訳が必要 → **編集ごとにタイムスタンプを打てば「修正労力 vs 品質」曲線**として報告可。
5. **実験デザイン上の交絡対策** — ウォッシュアウト期間(Hi-Seg 2026 preprint は4週間)、提示順ランダム化(実施済)、**オートメーションバイアス**の測定。脳動脈瘤読影(Radiol Med 2025)は偽陽性 AI 提示が疑いを有意に上げると実証(p=0.01)。**低データモデル(100〜500枚)の誤予測を初期提示する本設計では実在の脅威** → 専用解析または対照条件の価値あり。

## 追加計測の実装方針をユーザーと確定(調査・設計のみ・コード変更なし)

### 概要
- 上記の欠落5系統について、ユーザーが各論点に回答 → 本プロジェクトへの具体的な実装方針を確定した。
- 実験構成を再確認(`scripts/prepare_experiment.py` を Grep)。**216行目「chunk into 8 condition-mixed, gaze-balanced sessions of 10」**で、**8つの HITL セッションは1セッション10枚の中にモデル条件(seg100〜2500)が混在**(round-robin で条件を散らしてから10枚ずつ分割)、scratch のみセッション0固定と確定。→ 8条件比較には**画像ごとに主観負荷を取るしかない**(セッション末一括では盲検混在でどの条件の負荷か切り分け不能)。

### 確定した方針(5系統への対応)
1. **境界距離**: 許容幅は **3px**(1〜2pxのズレは許容、余裕を見て3px)。対象は **眼瞼(eyelid)のみ**(瞳孔/虹彩はアノテータ負荷を考慮し今回対象外)。眼瞼だけなら**構造サイズでのスケール不要=固定3pxで統一**。指標は **HD95・ASSD・Boundary-F1(=Surface Dice)@3px** を**保存済みポリゴンからオフライン計算**(UI変更不要)。「3px以内のズレは一致」の定義。
2. **主観的作業負荷**: フル NASA-TLX(加重版=6項目+15対比較で1枚2〜3分、非加重でも30〜45秒)はアノテーションより長く**画像ごとには非現実的**。→ **Paas の9段階メンタルエフォート単一項目尺度**(「今の作業にどれだけの精神的努力を要したか」1〜9、1問約5秒)を**全画像**で採用。計測タイミングは **submit(タイマー停止)後に分離**して回答させ、`duration_sec` に混入させない。多次元が欲しければ scratch セッション末に補助的にフル非加重TLXを足す案も温存。
3. **品質正規化した労力(NoC の翻訳)**: 既報の NoC@IoU(クリックで領域を育てる方式)はポリゴン頂点ドラッグ方式に直接使えない。→ **編集イベントごとにタイムスタンプを打ち**「Dice◯◯到達までに何回の頂点編集/何秒」=**修正労力 vs 品質の曲線**として表現し直す(⑤タイムスタンプ採用で実現可能)。
4. **オートメーションバイアス**: 専用の対照条件は**不要=後付け解析で十分**。(a) **scratch がアンカー無し基準**として効くので HITL 各条件の最終 Dice を scratch と比較、(b) **「最終アノテーションの GT 一致度」が「初期予測の品質」に相関するか**を既存 `correction_dice`・`area_change` と最終 Dice から見れば引きずりを直接検出(完全に直しきっていれば無相関のはず)。低データモデル(seg100〜500)の低精度予測を初期提示する本設計では実在の脅威だが、実験を増やさず解析で対応可。
5. **再現性(反復アノテーション)**: ユーザー了承。負担の小さい範囲で **各アノテータの後半セッションに5枚程度の再掲(同一条件)** を入れ、**個人内 test-retest** を ICC/ペアワイズ Dice で算出。個人間一致は Latin 方格で同一画像を3人が見るが**条件(モデル)が3人で異なり交絡**するため、クリーンな個人内再現性を優先。**タイムスタンプ記録もユーザー了承**。

## 境界指標を眼瞼のみ→全3クラスへ拡張・per-class カラムへリファクタ(実装・検証)

### 概要
- 上記実装直後にユーザーが「境界指標は眼瞼といったが、それでいいか? 他も計算するか?」と再確認。
- 「眼瞼のみ」は当初ユーザーが**アノテーター負荷を理由**に絞ったものだが、**境界指標は保存済みマスクからのオフライン計算でアノテーター負担はゼロ**なので、労力を理由に絞る必要が無いと整理。**全3クラス(eyelid/iris/pupil)で計算する**方針へ変更した。

### 判断の根拠
- 計算コストは実質ゼロ(オフライン)。
- **虹彩・瞳孔の境界ズレ(px)は臨床的に解釈しやすい** — 特に瞳孔は小さく Dice が過敏になりがちで、HD95/ASSD の絶対 px 値が「実際に何 px 外したか」を素直に示す。
- ただし虹彩・瞳孔は**楕円(5パラメータ)**なので、Boundary-F1@2px は固定許容幅ゆえ**小さい瞳孔ほど甘めに出る**点は認識(構造サイズでスケールしない方針どおり)。3指標の中では HD95/ASSD がより有用。
- 楕円は直接パラメータ比較せず、**`cv2.ellipse` で塗りつぶし→マスク境界のずれを測る**方式(眼瞼と同じ土俵=モルフォロジー勾配で境界抽出→距離変換で対称表面距離)。ユーザーの「楕円もマスク境界で測る方針」と一致。

### 実装内容
- `scripts/webapp/backend/scoring.py`: 境界指標の対象を眼瞼限定(`BOUNDARY_KEYS`)から**全クラス**へ拡張(各 per-class レコードで `boundary_metrics(sub_mask, gt_mask)` を無条件に算出)。
- `scripts/webapp/backend/session.py`: 眼瞼ハードコードの列(`eyelid_hd95`/`eyelid_assd`/`eyelid_boundary_f1`)を廃し、**per-class 共通方式**へリファクタ。CSV は各クラスに `{k}_hd95`/`{k}_assd`/`{k}_boundary_f1` を生成(`session.py:28`・`session.py:112-114`)。
- `tasks/todo.md`: 決定事項を「眼瞼のみ」→「全3クラス(オフライン計算でアノテーター負担ゼロのため)」へ更新。

### 検証
- フルパイプラインで **eyelid/iris/pupil の3クラス × hd95/assd/boundary_f1** の列がすべて生成されることを確認。GT をそのまま提出すると3クラスとも **HD95=0/ASSD=0/F1=1.0**。

## 努力尺度の目盛りを 1–9(Paas そのまま)で確定(意思決定のみ・コード変更なし)

### 概要
- ユーザーから「1–9 の9択でよいか? 医学の問診表だと 0–10 の numerical scale が多い」と確認。目盛り数の選択肢(0–10 / 1–9 / 1–10)とトレードオフを提示し、**ユーザーが 1–9(Paas 尺度そのまま)を選択**した。

### 判断とトレードオフ
- **1–9(Paas 1992)** = オリジナルの検証済み形式で、論文に「single-item cognitive load scale (Paas, 1992)」という**妥当性の確立した尺度として引用できる**のが最大の利点。→ 採用。
- 0–10(臨床 NRS 準拠, 0=なし)は眼科医に馴染みがあり無修正ケースの床を表現できる利点があったが、今回は**論文での引用可能性を優先**。
- 単一項目の妥当性の本質は「主観的精神的努力を1問で聞く」構成にあり、目盛り数(9/10/11)は混合効果モデルの連続量扱いにはほぼ影響しない。

### 状態
- **現在の実装がすでに 1–9 のため変更不要**(`app.js` の `_askEffort()` が 1〜9 ボタン生成、`effort` 列に 1〜9 記録)。運用時、最初のセッション/練習前に「1=非常に少ない〜9=非常に大きい」のアンカーを一言説明する運用メモのみ。
- これで**追加計測5項目+主観負荷尺度の仕様がすべて確定・実装・検証済み**。残タスクは ablation(U-Net)・実アノテーション施行・統計解析。
