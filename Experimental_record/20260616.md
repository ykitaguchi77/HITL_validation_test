## webapp アノテーション操作性の追加改修

### 概要
HITLアノテーションwebappに、アノテーション作業を高速化するUI操作を追加。

### 変更ファイル
- `scripts/webapp/static/js/tools.js` (編集)
- `scripts/webapp/static/js/app.js` (編集)
- `scripts/webapp/static/index.html` (編集)
- `scripts/webapp/static/js/canvas.js` (編集)

### 追加・修正した機能
1. **点追加(extend)時のエッジ挿入**: 選択中ポリゴンに新点を打つ際、末尾に単純追記すると遠い点同士が結ばれて図形が破綻していた。**新点に最も近い既存エッジ(線分)を求め、その2頂点の間に挿入**するよう変更。これで「もともとのエリアを広げる」自然な結ばれ方になる。
2. **クラス選択で即アクティブ化**: 図形がアクティブな状態で別クラスボタンを押すと、現在の図形を非アクティブ化して即座に次クラスのアノテーションへ移れるように変更。さらに「1クラス=基本1図形」の運用に合わせ、**クラス選択時に既存の同クラスポリゴンがあれば自動でactive**にする。
3. **スペースキーで点打ち + ウィンドウフィットボタン**: マウスクリックの代わりにスペースキーでも点を設置可能に。画像をビューポートに最大化する「フィット」ボタンを追加。
4. **矢印キーで1px移動**: 図形選択中に ↑↓←→ で画像座標1px移動(ポリゴンは全頂点、楕円は中心)。キーリピート中の連続移動は離した時に1コミット(=1 undo)、未選択時は無反応。
5. **塗りつぶしOFF**: 既存の 🎨 トグル(`fill` の alpha 0↔0.18、当たり判定維持)で対応済みのため新規ボタンは見送り。

### 検証
- 各機能をヘッドレス Playwright で実 `canvas.js`/`tools.js` を `python -m http.server` 配信し駆動して確認(検証用 `__*.html` ハーネスを多数作成、`scripts/webapp/static/__*test.html`)。

## 実験設計: 各セットを正面視7+周辺視3・提示順ランダム化

### 解析目的
各 phase(10枚)の視線方向構成を **正面視7枚+周辺視3枚に固定**し、提示順をランダム化したい。だが画像メタデータに視線方向の情報が無い。既存アノテーション(虹彩OBB・瞼ポリゴン)から視線方向を自動判定できるか検証する。

### 解析手法
- **虹彩偏心度 (iris eccentricity)** = 虹彩OBB中心 − 瞼ポリゴンbbox中心 を、瞼bboxサイズで正規化したベクトルの大きさ。大きいほど周辺視。
- 探索スクリプト `scripts/explore_gaze_eccentricity.py` を作成し、患者リーク無し test プール(id 2500-2999、症例安全)463枚で分布と閾値スイープを調査。
- 対象データ: `eyelid_caruncle_seg` / `obb_iris_pupil` の CVAT XML(`geometry.get_gt_annotation` でパース)。

### 主要な結果
- 全閾値で必要数(正面≥42・周辺≥18)は実現可能だったが、**`|ey|` 中央値(0.154)が `|ex|`(0.081)より大きい**ことを発見。これは解剖学的な縦方向ベースライン(正面視でも上眼瞼が虹彩上部を覆い、虹彩中心がbbox中心より下に来る)による底上げ。
- そのまま使うと**上方視が「中心=正面」と誤分類**される。→ **プール中央値で de-baseline**(偏心ベクトルから中央値を引いて正面視クラスタを原点化)してから大きさを取るよう補正。
- 補正後分布: p50=0.157, p70=0.276。**`ECC_THRESHOLD=0.20`** を採用 → 正面270枚 / 周辺193枚(36/19患者)で必要数に十分な余裕。
- 探索ロジックを `prepare_experiment.py` に統合し、探索スクリプトは削除。`experiment.json` を再生成。

### 変更ファイル

- `scripts/webapp/config/experiment.json` (再生成)

## リーク検証(真の held-out 患者で評価)・固定テストセット作成

### 依頼内容
ユーザーより「**結果が良すぎるのが気になります。リークしていないですよね??**」との懸念。報告中の Dice は各サブセット内部の検証分割(patient-grouped, その20%患者をhold-out)の値であり、本当に学習へ出ていない患者で測ると差が出ないかを確かめる。

### 検証(3段階で確認)
1. **内部 train/val 分割の患者非重複**: 全サブセットで `train_pat ∩ val_pat = 0`(patient-disjoint)を確認。seg100 の val が1患者(20枚)である点も把握。
2. **真に未知の患者(テスト域)で再評価**: 評価スクリプト `scripts/eval_on_heldout.py` を作成し、**学習に一切出ていない test-eligible 患者(min-id≥2500)**から **120枚 / 29患者**(全サブセットと患者・画像とも完全 disjoint)を取って、学習済み4モデルを **CPU で評価**(学習GPUに影響させない)。
3. 結果:

  | モデル | eyelid | iris | pupil | **mean** | (参考)内部val |
  |---|---|---|---|---|---|
  | seg100 | 0.943 | 0.933 | 0.880 | **0.919** | 0.922 |
  | seg200 | 0.951 | 0.936 | 0.893 | **0.927** | 0.937 |
  | seg300 | 0.959 | 0.942 | 0.907 | **0.936** | — |
  | seg500 | 0.972 | 0.957 | 0.918 | **0.949** | 0.971 |

### 結論: リークしていない ✅
- リークがあれば未知患者の値が内部 val より**大きく低下**するはず。実際は**ほぼ同等〜わずかに低い**(seg500: val 0.971 → test 0.949)で、これは正常な汎化ギャップ。
- 数値が高いのは**タスクが本質的に易しい**ため(瞼領域・虹彩/瞳孔の楕円という明瞭な構造を、クリーンな同一分布の臨床写真でセグメント)。旧 full-3000 モデルも 0.945 で同水準。
- 未知患者で **100→0.919 / 200→0.927 / 300→0.936 / 500→0.949** と素直な右肩上がり = HITL研究で狙った「データ量↑で改善」が**リークなしで確認**できた。

### 固定 held-out テストセットの作成

- 検証: 学習サブセットとの **画像オーバーラップ 0・患者オーバーラップ 0** を確認。

## 実験設計の相談: ブラインド vs ノンブラインド提示(結論未確定・継続中)

### 論点
HITLアノテーション効率の主要評価(モデル品質 → アノテーション工数)において、アノテータに
**どのフェーズ/モデルを編集中かを見せるか(ノンブラインド)/隠して混合提示するか(ブラインド)**を
どう設計するか。ユーザーからの設計相談。

### 進め方(外部LLMへのセカンドオピニオン併用)
- 同一の設問を **Codex CLI(`codex exec`)** と **Gemini CLI(`gemini -p`)** に投げ、私(Claude)の
  見解と合わせて3者で対比する方針で並行起動(read-only サンドボックス)。
- **環境上の注意(再現用)**:
  - `codex exec` は git リポジトリでない/未信頼ディレクトリだと停止 → **`--skip-git-repo-check`** が必要。
  - 再実行後も Codex は **401 Unauthorized(認証切れ)** で失敗 → `codex login` が必要(今回は取得できず)。
  - Gemini は応答待ちのままセッション終了(回答未取得)。
- 結果として外部2者の意見は揃わず、**私(Claude)の見解のみ提示済み**で中断。

### 私(Claude)の見解(提示済み・要旨)
1. **推奨: 8つのHITLモデル間はブラインド+ランダム混合提示。** 「弱い100枚/強い2500枚」と分かると初期
   予測への信頼度=編集量が変わり**期待バイアス**で交絡する。モデル名秘匿+混合提示で除去でき、順序/疲労
   効果も分散できる。
2. **各設計の妥当性脅威**: ノンブラインド=期待バイアス大・フェーズ順交絡。ブラインド混合=バイアスは除けるが
   **最大の脅威「画像難易度の交絡」は未解決**(条件ごとに別画像10枚だとモデル効果が画像差に埋もれうる)。
   単一アノテータ=一般化はケーススタディ的(3名以上が望ましい)。
3. **scratch は盲検化不可能**(空キャンバス vs 予測済みは見た目で明白)。よって盲検化できるのは
   **HITLモデル間のみ(部分盲検)**、scratch は識別可能な基準として混在させる。
4. **ランダム化案**: 全90枚を1〜数セッションにランダム混合・条件は裏で記録。画像難易度交絡対策は
   3名以上なら**ラテン方格**で画像↔条件割当をアノテータ毎に替える(やや大きめ改修)。1名なら交絡を受容し限界
   として明記、視線バランス(7+3)で一部統制。
5. **実装的本命=ハイブリッド**: ツールに**「ブラインド混合モード」**(全90枚シャッフル提示・初期予測の
   出所を非表示・条件は内部記録、scratch は空表示)を追加。小UI追加でバイアス統制の利益。デバッグ用に
   従来のフェーズ別(ノンブラインド)も残す。
   → この判断が**UIプランを分岐**: ノンブラインドなら「3フェーズをドロップダウン追加」だけ、ブラインドなら
   加えて「混合モード」を実装。

## 実験設計 Q2: Claude の前向き化・人数・パイロット・解析の見解(セッション末・回答待ち)

前節の Q2(アノテータ人数・前向き化・パイロット要否・解析法)を Codex に再依頼するも、**3モデル(gpt-5 /
gpt-5-codex / o4-mini)とも「ChatGPTアカウントでは非対応」で拒否・Gemini もクォータ枯渇**で外部意見は取得不可。
そこで私(Claude)の見解のみ提示した。

### 私(Claude)の Q2 見解(要旨)
1. **前向き化: はい(軽量に)**。探索的効率研究なので厳密な確認試験は不要だが、**人数・条件・主要アウトカム・
   解析法を事前固定**(短い解析計画書)して p-hacking を回避し公表に耐えるようにする。
2. **アノテータ人数: 3〜5名(最低3名)**。被験者内反復測定で画像レベル観測数は N×90 と多く、**用量反応カーブ
   (工数 vs モデルサイズ)は少人数でも検出可能**。律速はアノテータ間一般化(ランダム効果)。N=1=ケーススタディ、
   N=3 で「複数評価者で再現」、N=5 で安定。専門医希少のため 3〜5 が現実的。
3. **専用パイロット不要 → 内部パイロット**。1人目を内部パイロットにし動作確認・効果量/分散把握を兼ね、**その
   データも本解析に組入れ**(プロトコル不変なら破棄不要)。新規HCI指標では事前検定力計算は当てにならず内部実測が有用。
4. **解析: 混合効果モデル** `outcome ~ 条件(or log学習枚数) + gaze + (1|アノテータ) + (1|画像)`。
   **画像をランダム効果にして画像難易度の交絡を一部吸収**。scratch vs HITL は別対比。
