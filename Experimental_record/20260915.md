### 1. 論文の筋書き(提示内容)
- **問い**: セグメンテーションモデルは何枚の学習データから アノテータの労力を実質的に減らし始め、
  どこで頭打ちになるか(=手描き→モデル支援へ切り替えるべき時点)。
- **タイトル案**: *How much training data does a segmentation model need to help its annotators?
  A blinded within-subject study of human-in-the-loop annotation efficiency versus model maturity in periocular images*
- **Methods 要約**: 3クラス(eyelid/iris/pupil)・患者リーク無し nested サブセット 100〜2500 枚で学習した
  SegFormer-B1 ×8(固定 held-out 463枚の Dice 0.919→0.958(ピーク seg2000)、500〜1000枚で飽和傾向)、
  独自 webapp、9条件(scratch + HITL×8)×10枚、3×9 Latin 方格、HITL 8条件は盲検混合提示、練習2種、
  末尾に同一条件再掲(Session 9, test-retest)。指標は主要=作業時間、副次=クリック/頂点編集/マウス移動、
  Dice/IoU、HD95/ASSD/Boundary-F1@2px、Paas 主観負荷、初動/アイドル時間、correction Dice。
- **統計**: 画像・アノテータを含む混合効果モデル。**主解析は log(学習枚数) に対する用量反応(トレンド)**とし、
  8条件の総当たり比較にはしない。scratch との対比は別建て。品質は非劣性マージン(例 Dice 差 −0.01 以内)を事前設定。
- **Results 図表案**: ①デザイン図 ②モデル Dice vs 学習枚数 ③作業時間/クリック/主観負荷 vs 学習枚数
  (scratch を水平基準線で併記、**飽和点 knee が主結果**) ④最終品質 vs 学習枚数 ⑤オートメーションバイアス
  (correction Dice と最終 Dice の相関、scratch 比較) ⑥補助(ICC・アノテータ別・修正労力 vs 品質曲線)。
- **Discussion の核**: 効率の飽和点がモデル Dice の飽和点と一致するか遅れるか。横軸を枚数だけでなく
  **held-out Dice** でも報告すると他タスクへ転用可能な指針になる。

### 2. 被検者3名で十分か(結論: 最低限成立、主張の書き方に制約)
- 被験者内・画像反復型で解析単位は画像アノテーション(本解析 270 + 再掲 30)。scratch vs HITL のような
  大きな差は3名で検出可。**隣接条件(例 seg1500 vs seg2000、各30観測)の対比は検出力不足**なので
  トレンド解析を主にする方針が3名設計の生命線。
- 先行研究も2〜5名が多く(文献ノートでは Vision6D の11名が例外)、3名は査読で即却下される数ではない。
- **統計上の真の問題**: 水準3のランダム効果は分散推定が不安定 → アノテータは**固定効果**として扱い
  「結論はこの3名に対するもの」と限定。3名の経歴(専門医/研修医/技師等)と異質性を明記。
- **拡張余地**: `scripts/prepare_experiment.py:195` 付近の Latin 方格は cyclic で `ANNOTATOR_NAMES` を
  増やすだけで最大9行まで拡張可。査読で人数を求められた場合、画像セットを変えずに4〜6人目を追加できる
  (追加後に既存3名の割当が不変であることを再生成後に検証する必要あり)。可能なら最初から5〜6名が望ましい。

### 3. 論文化で問題になりうる点(優先度順)
1. **scratch が常にセッション0(非盲検・最初)** → 習熟が浅い時期に scratch を行うため scratch が遅く見え
   HITL 効果を過大評価する方向のバイアス。対策案 (a) **最終セッションとして scratch 10枚を追加**(前後差から
   学習効果を推定、1人 10〜20分の追加負担・推奨) (b) 少なくとも scratch 内スロット順の時間推移を報告。
2. **GT スタイル継承バイアス** → GT は単一作成者、モデルはその GT で学習しているため HITL 成果物が GT の癖に
   寄り GT-Dice で有利。境界指標併記・Discussion で明示。scratch 画像の一部を3名共通にすると人間間ばらつきの
   上限が得られる。
3. **主要評価項目と多重性** → 指標が約10あるので主要(作業時間)/副次を**データ収集前に文書化**(軽量事前登録)。
4. **倫理審査** → 患者画像二次利用に加え、アノテータが研究参加者になるため同意手続きが必要。
5. **学習曲線が単一 run** → 100〜500 だけでも seed を変えて2〜3回学習し誤差棒を付けると説得力向上。
6. **U-Net ablation** → 人間実験を伴わない Dice 曲線のみなら価値限定的。スコープを絞るなら落としてよい。
7. **疲労・分割実施** → 1人約106枚で2〜3.5時間。実施日・休憩をログに残し複数日運用を決めておく。
8. 軽微: タイミング・サイドチャネル対策(予測事前計算)未実装だがウォームアップで実害小、
   Boundary-F1@2px は瞳孔で甘めに出る点は既知。
- 投稿先の目安: TVST / Ophthalmology Science / Scientific Reports / IJCARS / CMPB。

## 追記: 虹彩・瞳孔アノテーションが課題に含まれているかの確認(Q&A・コード変更なし)

### 概要
- ユーザーから「虹彩や瞳孔のアノテーションも含まれていたか」の確認質問。
  `scripts/webapp/backend/config.py:46` を参照して **Eyelid / Iris / Pupil の3クラス**が現行課題であることを確認
  (Caruncle は 6/18 に Eyelid へ統合して廃止済み)。

### 確認した内容
| クラス | 図形 | 操作 | GT/モデル |
|---|---|---|---|
| Eyelid | ポリゴン | 頂点ドラッグ・点追加・複数選択移動 | CVAT の Eyelid∪Caruncle 統合外形 / SegFormer eyelid チャネル |
| Iris | 回転楕円(OBB) | 移動・リサイズ・回転 | CVAT 楕円 / iris チャネルから楕円フィット |
| Pupil | 回転楕円(OBB) | 同上 | 同上 / pupil チャネル |

- HITL 条件では3クラスすべてがモデル予測でプレフィルされ、scratch では3つとも手描き。
- 3クラス揃わないと提出できないガードあり(実験96画像・候補プール463枚で瞳孔欠損ゼロを検証済み)。
- 計測・スコアは per-class(Dice/IoU、HD95/ASSD/Boundary-F1@2px は楕円も `cv2.ellipse` 塗りつぶしで境界算出、
  クラス別クリック/頂点編集/時間内訳も記録)。周辺視3枚/セッションは楕円の傾き操作を確実に発生させる目的。
- モデル held-out Dice も3クラス別(例 seg2500: eyelid 0.975 / iris 0.961 / pupil 0.927 — 瞳孔が最難)。

### 論文への含意
- 「ポリゴン修正(眼瞼)」と「楕円パラメータ修正(虹彩・瞳孔)」は労力の質が異なるため、
  **クラス別に効率曲線を出す**のが自然。瞳孔は小さく Boundary-F1@2px が甘めに出るので HD95/ASSD の絶対 px 値を併記する方針。

## 追記2: クラス別の手間(労力)をログから計算できるかの確認(Q&A・コード変更なし)

### 概要
- ユーザーから「クラス別にどれぐらいの手間がかかったかはログから計算可能か」の確認質問。
  `scripts/webapp/static/js/metrics.js`・`scripts/webapp/backend/session.py`・`scripts/webapp/static/js/app.js`
  を読み直し、**既にクラス別の労力指標が `summary.csv` の列としてそのまま保存されている**ことを確認して回答。

### 確認した内容(eyelid / iris / pupil それぞれ、`session.py` の `_per_class_cols()`)
| 列 | 意味 |
|---|---|
| `{k}_time_sec` | そのクラスを選択していた作業時間(一時停止分は除外) |
| `{k}_clicks` | そのクラス選択中のクリック数 |
| `{k}_vertices_edited` | 頂点の追加・移動・削除数 |
| `{k}_correction_dice` / `{k}_area_change` | HITL でプレフィルをどれだけ変えたか(修正量) |
| `{k}_dice` / `_iou` / `_hd95` / `_assd` / `_boundary_f1` | 品質 |
| `{k}_gt_present` / `{k}_submitted_present` | GT/提出物の有無 |

- JSONL の `events[]` は全操作が `{t, type, cls}` 形式でタイムスタンプ付きなので、クラス別の
  「初動時間」「アイドル時間」「編集数の時系列(修正労力 vs 品質曲線)」もオフラインで再構成可能。

### 仕組みと解釈上の注意点
- 時間の帰属は「右サイドバーで選択中のクラス」で決まる(`metrics.js` の `setActiveClass`/`_flushClassTime`)。
  クラス選択はサイドバーのみ(canvas クリックでは切り替わらない)ので帰属は明確。
- **画像表示直後は eyelid が既定で選択される**(`app.js` の `this.setActiveClass("eyelid")`)ため、
  全体を眺める・ズームする等の「クラス非依存の時間」は eyelid に乗る。3クラス合計は `duration_sec` と一致するはずだが
  **eyelid はやや過大評価**される(events から「最初の操作までの時間」を差し引く補正は可能)。
- 楕円(iris/pupil)の移動・リサイズ・回転は「頂点編集」ではないので `{k}_vertices_edited` には乗らず、
  時間・クリック・correction_dice で見る。
- `mouse_distance_px` は全体のみでクラス別はない。必要なら events の `cls` で mouseMove を帰属させる小改修が要る。

### 結論
- 「眼瞼(ポリゴン修正)と虹彩・瞳孔(楕円修正)で、モデル成熟に伴う手間の減り方が違うか」を示す材料は
  **現行ログで揃っている**。追加実装は不要(クラス別マウス距離が欲しい場合のみ小改修)。

### 追体験で描いた流れ(要点)
- ログイン: 配布 URL → Basic 認証(`annotator`/共有パスワード) → アノテータ選択(先頭の「動作テスト用」を選ばないよう注意)。

  Iris/Pupil は楕円(E)。周辺視画像では Transformer で楕円を回転させる必要があり**ここが最も戸惑う操作**。
  提出後の確認画面で GT 点線と Dice が出て自分の癖(外側を広く取りすぎ等)が分かる → 負担度(Paas 1〜9)。

  モデル名が出ないので「今日は弱いモデル」とは思えず1枚ごとに判断。「直すより消して描き直す方が早いのでは」と迷う場面がある。
  10枚ごとに一覧へ戻り「✓ Session N (10枚)」、休憩・別日継続が可能。フォーカス喪失で一時停止オーバーレイ。S9 は他と区別がつかない。
- 総負担: 練習6 + 本番100 = 106枚、1枚 1〜1.5分で**合計 2〜3時間**。Scratch+2セッションを1日目、残りを2〜3日に分ける運用が現実的。

### 被験者として引っかかった点(実施前に潰せるもの)
1. **ガイドの記載が古い**: `annotator_guide.md` L14 は「アノテータ番号 `1`/`2`/`3` を選択」だが、実画面は実名

   「GT との差 2px 以内なら一致扱い」と伝えるかどうかは検討事項。
5. **休憩・分割実施の目安**(1日に何セッション)がガイドに無い。

### なぜ必要か
- 現設計では scratch の時間が「ツールに慣れる前」の値になり、査読者は必ず「scratch が遅いのは順序効果では?」と問う。
- 末尾に scratch を再度置くと**同一人物の「習熟前 vs 習熟後の scratch」**が得られ、順序効果の大きさそのものを報告できる。
  1人あたり 20〜30 分の追加負担で設計最大の弱点を潰せる。

### 画像の選び方(3案比較)
| 案 | 画像 | 得られるもの | 弱点 |
|---|---|---|---|
| **A: セッション0と同じ10枚を再描画(推奨)** | 既出 scratch 画像 | 順序効果を**画像で対応づけた差**として最も高感度に推定(30ペア)。scratch の個人内再現性(Session 9 の HITL 版と対になる) | 画像の記憶。ただし100枚・数時間〜数日を挟んだ手描きへの影響は小さい |
| B: 新規10枚を3人共通ブロックに | 未使用画像(プール余裕あり) | **3人の scratch 間一致度**=人間間ばらつきの上限(GT スタイル継承バイアスの議論材料) | 順序効果と画像難易度が交絡(その10枚は「末尾 scratch」でしか観測されないため分離不能) |
| C: HITL で見た画像10枚を scratch で | 既出 HITL 画像 | 同一画像での scratch vs HITL 対比較 | 直前に直した予測の記憶が強く残り scratch として汚れる |

  B の人間間一致度は魅力的だが順序効果と分離できない設計は本末転倒。A+B 併用は1人 120枚超で負担過大。

- scratch の ICC を Session 9 の HITL ICC と並べて報告可能。
